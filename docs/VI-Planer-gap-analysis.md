# VI Planer — gap-анализ vs целевой контур приоритизации

**Дата:** 15.09.2026  
**База сравнения:** текущий VI Planer (SPA + Supabase/API, master) vs целевое ТЗ (Jira + сессии + роли PMO/продукт).  
**Важно:** интеграция с Jira **не реализована** и в v1 явно out of scope.

**Live:** https://bolshakovin.github.io/vi_planer/  
**PDF:** [VI-Planer-gap-analysis.pdf](./VI-Planer-gap-analysis.pdf)

---

## 1. Краткий вердикт

VI Planer закрывает **портфельное планирование ёмкости** (RICE, сквозной приоритет, Gantt, очереди команд). Целевое ТЗ — **управляемое изменение приоритетов** на базе Jira/Structure с окном встречи, RBAC и аудитом. Это **разные продукты**: пересечение по сущности «приоритет в таблице» и разделению продукт/проект; расхождение по платформе, governance и финансовым полям.

---

## 2. Что уже покрывает (полностью / частично)

| Целевое | Сейчас | Оценка |
|---|---|---|
| Сквозной числовой приоритет + перенумерация | `manualRank`, drag ⋮⋮, confirm конфликта | Частично (без сессии/аудита) |
| Два контура продукт / проект | `type: product\|project`, фильтр, бейджи; справочники продуктов/проектов — в работе | Частично (один общий ранг, не два независимых бэклога) |
| Таблица: имя, статус, исполнитель, заказчик, маечная оценка | Портфель + карточка; заказчик/исполнитель в модели; вкладка «Роли» ещё не в навигации | Частично |
| Дата завершения / старт работ | Расчёт bottleneck + `workStartDate` по командам | Частично (не «актуальная/первоначальная» даты из Jira) |
| Просмотр «для всех» | Публичный SPA без auth | Частично (нет разграничения прав) |
| What-if по ёмкости / Gantt | Режимы утилизации, очереди, PDF-экспорт | Сверх ТЗ (целевое ТЗ этого почти не требует) |
| Хранение | Supabase / API / localStorage | Иное (не Jira) |

## 3. Пробелы (отсутствует)

### Governance и сессии
- Модель **встречи / сессии**: «Открыть сессию» / «Закрыть сессию»
- Привязка к **Yandex Calendar**, тип «Планирование приоритетов», keywords
- Edit **только в окне встречи**; вне окна — read-only
- Исключение **главы PMO** после закрытия периода + обязательная причина
- **Snapshot** после закрытия для ретро
- История изменений приоритета / полей; обязательный **комментарий → Jira comment**

### Роли и контуры
- Роли: любой viewer / PMO admin / product team (свой folder)
- Запрет чужого контура; PMO правит только Projects
- Режим UI «Проекты» | «Продукты» как **отдельные пространства приоритетов**
- Иерархия **Structure** (folders), домены «Product — PMO-tag»
- Справочник команд продуктов ↔ функциональности из Jira

### Данные таблицы (целевые колонки)
- Код задачи (Jira key)
- Первоначальная / актуальная даты завершения (как поля трекера)
- Дата создания задачи; старт после status ≠ new
- **ЧП** и **ROI** (RUB, 12 мес.)
- Ограничение editable-полей на встрече: только приоритет, актуальная дата, майка, статус

### Платформа
- Jira API / Forge / Connect / Structure sync
- Auth/SSO и RBAC (сейчас NFR-07: публичный store без auth)
- Запрет пустого приоритета как жёсткое правило сессии (сейчас ранг нормализуется клиентом, но без session gate)

## 4. Противоречия (VI Planer vs целевое видение)

| Тема | VI Planer сейчас | Целевое ТЗ |
|---|---|---|
| Платформа | Отдельный Vite SPA; данные Supabase/API | Интерфейс **на базе Jira** + Structure |
| Когда менять приоритет | В любой момент (drag / поле) | Только в **запланированной встрече** (кроме главы PMO) |
| Модель приоритета | Ручной ранг **+ RICE** как score | Meeting-bound reorder; RICE не заявлен |
| Контуры | Один список, фильтр product/project | Два независимых контура с разными правами |
| Безопасность | Нет пользователей/ролей | RBAC + запрет чужого folder |
| Аудит | Нет истории изменений | Полная история + Jira comments |
| Фокус продукта | «Когда закончим» (capacity/Gantt) | «Кто/когда может менять приоритет» (governance) |
| Roadmap v1 | Jira, auth, audit — **out of scope** | Это **ядро** целевого решения |

**Вывод по стратегии:** доработки «поверх SPA» не закроют Jira-native vision без смены платформы или глубокого sync-слоя. Имеет смысл явно выбрать: (A) эволюция VI Planer как planning twin, (B) новый Jira-модуль governance, (C) гибрид (VI Planer читает Jira, пишет приоритеты обратно только из сессии).

## 5. Бэклог доработок (приоритет)

### Must
1. **Решение по архитектуре (A/B/C)** — без него остальные эпики расходятся.  
2. **Сессии планирования** (open/close, read-only вне окна, snapshot) — ядро целевого процесса.  
3. **RBAC контуров** (PMO ↔ Projects; PM ↔ свой Product) — без этого «правила» не enforceable.  
4. **Обязательный комментарий + audit log** на смену приоритета/статуса/майки/даты.  
5. **Два независимых ранга** (project backlog / product backlog) + явный режим UI.

### Should
6. Интеграция календаря (Yandex) / keywords типа встречи.  
7. Синхронизация с Jira (key, status, assignee, комментарии) — если выбран путь A или C.  
8. Расширение таблицы: key, даты создания/базовой/актуальной, фильтр доменов.  
9. Жёсткий запрет пустого приоритета и чужого контура на уровне API.  
10. Исключение главы PMO post-close с формальной причиной.

### Could
11. Поля ЧП / ROI (12 мес., RUB) и отображение в таблице.  
12. Structure-like дерево / импорт иерархии folders.  
13. Ретро-сравнение snapshots сессий.  
14. Сохранение RICE/Gantt как **аналитического** слоя рядом с meeting-priority (ценность текущего VI Planer).

---

## 6. Сценарии ТЗ → покрытие

| Сценарий | Покрытие |
|---|---|
| Встреча PMO, контур Projects | Нет сессии/календаря; приоритет меняется всегда |
| Product manager, контур Products | Фильтр type=product есть; нет изоляции прав |
| View-only вне окна | Нет (все могут писать в shared store) |
| Глава PMO после закрытия + причина | Нет ролей и post-close workflow |

---

## 7. Рекомендация

Краткосрочно: зафиксировать gap-анализ как вход в продуктовое решение **A/B/C**.  
Если цель — compliance приоритизации PMO: начинать с **сессий + RBAC + audit** (даже на текущем SPA) как прототип правил, параллельно оценивая Jira Forge/Structure.  
Не позиционировать текущий RICE/Gantt SPA как уже реализованный «Jira priority control» — это вводит в заблуждение стейкхолдеров.
