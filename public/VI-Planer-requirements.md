# VI Planer v1 — требования

Документ описывает бизнес-требования, use cases, функциональные и нефункциональные требования для **замороженной редакции v1**.

**Редакция:** v1 (путь GitHub Pages `/v1/`, отдельный бандл). Живая редакция v2 — отдельно: корень SPA, см. `docs/VI-Planer-requirements.md` / `public/VI-Planer-requirements.md`.

Актуально для UI v1: вкладки **Портфель → Gantt/Сроки → Очередь команд → Мониторинг → Команды → Роли → Проекты → Журнал → Настройки**; сквозная сущность **функциональность**; приоритет **RICE**; **дата завершения**; хранение GitHub Pages + Supabase / API; PDF без CDN.

**Изоляция данных v1:** localStorage `vi-planer-v3`, облачная строка `app_state.id = 'main'`, ключ вкладки `vi-planer-v1-ui-tab`. Переключатель v1/v2 в шапке **не** должен очищать и перезаписывать хранилище другой редакции.

---

## 1. Продуктовая цель

Дать командам **единый портфель функциональностей** (в продуктах и проектах) со сквозным приоритетом и расчётом даты завершения по реальной ёмкости команд, чтобы отвечать:

- «что делаем первым»;
- «когда закончим»;

без разрозненных бэклогов.

### Бизнес-цели (BR)

1. Единый сквозной приоритет между продуктами и проектами.
2. Честная дата завершения с учётом ёмкости и очередей нескольких команд.
3. Прозрачность кросс-командных функциональностей и bottleneck.
4. Быстрый what-if по FTE/ёмкости и маечной оценке без смены трекера.
5. Справочники заказчиков / исполнителей и каталоги проектов / продуктов.
6. Доступ по ссылке для команды без установки ПО.

### Out of scope (v1)

Auth/RBAC, полноценный audit/approval workflow приоритета, интеграция Jira/Linear, удаление команд, native mobile, realtime multiplayer, мультитенантность, импорт/экспорт JSON из шапки. Вкладки **Потребность** / **Планирование** с ролями потребности (как в v2) — **не** часть v1 (это эволюция v2). Мониторинг — демо read-only.

## 2. Акторы

| ID | Актор | Цель |
|---|---|---|
| A1 | Product / Portfolio Owner | Единый приоритет и дата завершения по всему портфелю |
| A2 | Team Lead | Очередь своей команды и загрузка ёмкости |
| A3 | Stakeholder / коллега | Просмотр плана и экспорт PDF по ссылке |
| A4 | Администратор развёртывания | Опубликовать замороженный `/v1/` и store `main` |

## 3. Use cases

### UC-01 — Просмотреть единый портфель

- **Акторы:** A1, A2, A3  
- **Триггер:** открытие `/v1/` / вкладка «Портфель» / клик по логотипу «VI Planer»  
- **Предусловия:** загружено состояние (облако `main` / API / localStorage `vi-planer-v3` / демо)  
- **Основной сценарий:**
  1. Система показывает метрики: активные функциональности, горизонт, команды под риском, старт планирования.
  2. Система показывает таблицу функциональностей (тип, команды с маечной оценкой, статус, RICE, оценка, дата завершения).
  3. Пользователь может раскрыть «Адженда» с легендой колонок.
- **Альтернатива:** нет данных → заполнение демо-seed.  
- **Постусловие:** пользователь видит актуальный портфель.

### UC-02 — Отфильтровать и отсортировать портфель

- **Акторы:** A1, A2  
- **Триггер:** фильтр / клик по заголовку колонки  
- **Сценарий:** поиск, тип, команда, статус; сортировка по Приоритет / RICE / Оценка / Дата завершения; сброс фильтров.  
- **Постусловие:** таблица отражает выбранный срез.

### UC-03 — Создать функциональность

- **Актор:** A1  
- **Триггер:** «+ Функциональность»  
- **Сценарий:** заполнение полей (название, тип, продукт/проект, статус, заказчик, исполнитель, RICE, приоритет, заметки); назначение ≥1 команды с маечной оценкой (XS–XXL) и стартом (понедельник); live RICE / дата завершения; сохранение.  
- **Альтернативы:** нет команд → alert; Отмена/Закрыть → без сохранения.  
- **Постусловие:** функциональность в портфеле, приоритеты уникальны 1…n.

### UC-04 — Редактировать / удалить функциональность

- **Актор:** A1  
- **Триггер:** клик по строке  
- **Сценарий:** изменение полей и команд → Сохранить.  
- **Альтернатива:** Удалить (без доп. confirm).  
- **Постусловие:** портфель и расписание пересчитаны.

### UC-05 — Изменить сквозной приоритет

- **Актор:** A1  
- **Триггер:** ввод ранга / drag ⋮⋮  
- **Предусловие drag:** сортировка по «Приоритет»  
- **Сценарий:** новый ранг; при конфликте — confirm; переиндексация 1…n; drag в видимом списке.  
- **Альтернативы:** drag при другой сортировке недоступен; отказ в confirm.  
- **Постусловие:** очереди и Gantt следуют новому порядку.

### UC-06 — Управлять командами и ёмкостью

- **Акторы:** A2, A1  
- **Триггер:** вкладка «Команды»  
- **Сценарий:** название и capacity у команд; создание команды с цветом; пересчёт даты завершения / риска.  
- **Альтернатива:** удаление команды — вне scope v1.

### UC-06b — Настроить маечную оценку и старт планирования

- **Акторы:** A1, A2  
- **Триггер:** вкладка «Настройки»  
- **Сценарий:** диапазоны дней XS–XXL; дата старта планирования; пакет портфеля / откат.  
- **Постусловие:** оценки и горизонт пересчитаны.

### UC-06c — Управлять ролями (справочники)

- **Акторы:** A1  
- **Триггер:** вкладка «Роли»  
- **Сценарий:** справочники заказчиков и исполнителей; выбор в карточке функциональности.  
- **Постусловие:** списки `customers` / `executors` обновлены.

### UC-06d — Управлять каталогами проектов / продуктов

- **Акторы:** A1  
- **Триггер:** вкладка «Проекты»  
- **Сценарий:** списки имён проектов и продуктов для поля backlog в карточке.  
- **Постусловие:** `projects[]` / `products[]` обновлены.

### UC-07 — Просмотреть очередь команд

- **Акторы:** A2, A1  
- **Триггер:** «Очередь команд»  
- **Сценарий:** единый вид по всем командам: очередь по приоритету, план/сдвиг, даты, «может взять с…» / причина, утилизация 8 нед.; режимы утилизации (как на Gantt); тоггл «Показать загрузку команд».  
- **Постусловие:** пользователь видит загрузку и слоты команд.

### UC-08 — Просмотреть сроки (Gantt)

- **Акторы:** A1, A3  
- **Триггер:** «Gantt/Сроки»  
- **Сценарий:** полоски по командам, bottleneck, зависимости очереди (в последовательном режиме); горизонт 4–52 нед.; кнопки **Последовательная** / **Максимальная** утилизация (повторный клик → «Как задано»); опционально полосы загрузки команд.  
- **Альтернатива:** статус «Готово» исключается из расписания.

### UC-08b — Просмотреть мониторинг (демо)

- **Акторы:** A1, A3  
- **Триггер:** вкладка «Мониторинг»  
- **Сценарий:** read-only: загрузка команд и комплектация (доля функц. с командой + заказчиком + исполнителем).  
- **Постусловие:** пользователь видит демо-метрики без редактирования на вкладке.

### UC-08c — Просмотреть журнал изменений

- **Акторы:** A1, A2  
- **Триггер:** вкладка «Журнал»  
- **Сценарий:** список недавних изменений в приложении.  
- **Постусловие:** пользователь видит локальный журнал.

### UC-09 — Сохранить и синхронизировать данные (только v1)

- **Акторы:** A1, A2  
- **Триггер:** любое изменение  
- **Сценарий:** localStorage `vi-planer-v3` сразу; debounce → Supabase row `main` и/или API state v1; индикатор синхронизации в шапке. Ключи v2 **не** должны пересекаться при корректной изоляции.  
- **Альтернатива:** API/облако недоступны → локальный fallback.

### UC-10 — Скачать PDF текущей вкладки

- **Акторы:** A1, A3  
- **Триггер:** «Экспорт PDF» в шапке  
- **Сценарий:** цветной landscape A4 PDF метрик + активной вкладки; html2canvas и jspdf бандлятся с приложением (без CDN).  
- **Альтернатива:** ошибка захвата → alert.

### UC-12 — Открыть приложение по публичной ссылке `/v1/`

- **Акторы:** A3, A4  
- **Сценарий:** GitHub Pages `/vi_planer/v1/` (+ Supabase shared `main`) / API с отдельным state для v1.  
- **Альтернатива:** Pages без Supabase → данные per-browser.

### UC-13 — Вернуться на главную (Портфель)

- **Акторы:** A1, A2, A3  
- **Триггер:** клик по бренду «VI Planer» в шапке  
- **Сценарий:** активная вкладка переключается на «Портфель».

### UC-14 — Переключить редакцию v1 ↔ v2

- **Акторы:** A1, A3  
- **Триггер:** переключатель в шапке  
- **Сценарий:** переход на v2 (корень) или остаться на `/v1/`; данные редакций изолированы.  
- **Постусловие:** чужой store не wipe.

## 5. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Производительность | Пересчёт портфеля ≤ 200 мс (~50 функциональностей, ~10 команд) |
| NFR-02 | Производительность | Первая отрисовка UI ≤ 3 с |
| NFR-03 | Надёжность | localStorage сразу; remote debounce ≤ 500 мс |
| NFR-04 | Надёжность | При недоступности API/облака — локальный режим |
| NFR-05 | Доступность | Chrome/Edge/Safari last 2; desktop-first от 1280px |
| NFR-07 | Безопасность | Публичный shared store без auth (внутренний прототип); row id = `main` |
| NFR-08 | Безопасность | Валидация/нормализация AppState на клиенте и сервере |
| NFR-09 | Совместимость | Относительные ассеты; base path `/vi_planer/v1/` |
| NFR-10 | Развёртывание | Сборка из ветки/тега `v1` → `dist-pages-v1` → `docs/v1/` |
| NFR-11 | Наблюдаемость | GET /api/health (при API-бэкенде) |
| NFR-12 | i18n | UI на русском |
| NFR-13 | Масштаб | До 200 функциональностей, до 20 команд |
| NFR-14 | Офлайн | Работа из localStorage; PDF из бандла приложения (без внешней CDN) |
| NFR-15 | Изоляция | v1 не должна читать/писать store v2 (`vi-planer-v2`, cloud `v2`) |

## 6. Модель данных (v1)

### AppState
`version` (3), `startDate`, `teams[]`, `items[]`, `sizeRanges` (XS…XXL → min/max дней), `customers[]` / `executors[]`, `projects[]` / `products[]`, `changeLog[]`, опционально пакет портфеля

### Team
`id`, `name`, `capacityPw`, `color` (+ состав/роли — по состоянию ветки v1)

### WorkItem (функциональность)
`id`, `title`, `type` (product|project), `backlog`, `status`, `owner` (Заказчик), `assignee` (Исполнитель), `assignments[]`, `reach`, `impact`, `confidence`, `notes?`, `manualRank`

### TeamAssignment
`teamId`, `size` (XS…XXL), `workStartDate` (понедельник)  
Effort в чел·нед = midpoint диапазона дней / 5 (не меньше 1 нед.).

### Расчётные (не persist)
`ScheduledSlice`, `ItemSchedule`, `TeamLoadWeek` — очереди, дата завершения, bottleneck, загрузка по неделям.

### Ключи хранения (только эта редакция)
| Слой | Ключ / id |
|---|---|
| localStorage state | `vi-planer-v3` |
| localStorage UI tab | `vi-planer-v1-ui-tab` |
| Supabase / Postgres | `app_state.id = 'main'` |
| HTTP API | state edition v1 (`/api/state` / `/api/state/v1` — по контракту бэкенда) |

## 7. Критерии приёмки (smoke)

1. Создать функциональность на 2 команды с маечной оценкой.  
2. Изменить приоритет drag.  
3. Включить Последовательную или Максимальную утилизацию и увидеть сдвиг даты завершения на Gantt.  
4. Открыть вкладки Роли / Проекты / Журнал — справочники и журнал доступны.  
5. Экспорт PDF с активной вкладки (без CDN).  
6. Перезагрузить `/v1/` — данные в `vi-planer-v3` / cloud `main` сохранились.  
7. Переключить на v2 и обратно — данные v1 не стёрты.  
8. Клик по «VI Planer» → Портфель.  
9. Скачать PDF требований; открыть PDF презентации.
