# VI Planer v2 — требования

Документ описывает бизнес-требования, use cases, функциональные и нефункциональные требования для **редакции v2** (основной / default SPA).

**Редакция:** v2 (корень Pages / live SPA). Замороженная v1 — отдельно: путь `/v1/`, см. `docs/v1/VI-Planer-requirements.md`.

Актуально для текущего UI: вкладки **Реестр → Потребность → Планирование → Гант → Очередь команд → Команды → Журнал → Настройки** (+ опционально **Мониторинг**); сквозная сущность **функциональность**; приоритет **RICE**; **дата завершения**; хранение GitHub Pages + Supabase / API; PDF без CDN.

**Изоляция данных v2:** localStorage `vi-planer-v2`, облачная строка `app_state.id = 'v2'`, API `/api/state/v2`, ключ вкладки `vi-planer-v2-ui-tab`. Переключатель v1/v2 в шапке **не** очищает и не перезаписывает хранилище другой редакции.

---

## 1. Продуктовая цель

Дать командам **единый портфель функциональностей** (в продуктах и проектах) со сквозным приоритетом, потребностью по ролям, планированием исполнителей и расчётом даты завершения по реальной ёмкости команд, чтобы отвечать:

- «что делаем первым»;
- «когда закончим»;
- «насколько комплектация заполнена»;

без разрозненных бэклогов.

### Бизнес-цели (BR)

1. Единый сквозной приоритет между продуктами и проектами (Реестр).
2. Потребность по командам и ролям (в т.ч. **бизнес-аналитик**) с оценкой в днях / майке.
3. Планирование исполнителей из состава команд (роль—ФИО).
4. Честная дата завершения с учётом ёмкости и очередей нескольких команд.
5. Прозрачность кросс-командных функциональностей, bottleneck и демо-мониторинга комплектации.
6. Быстрый what-if по FTE/ёмкости и маечной оценке без смены трекера.
7. Доступ по ссылке для команды без установки ПО.

### Out of scope (v2)

Auth/RBAC, полноценный audit/approval workflow приоритета, интеграция Jira/Linear, удаление команд, native mobile, realtime multiplayer, мультитенантность, импорт/экспорт JSON из шапки. Мониторинг — **демо read-only** макет, не полноценный BI.

## 2. Акторы

| ID | Актор | Цель |
|---|---|---|
| A1 | Product / Portfolio Owner | Единый приоритет, потребность и дата завершения по портфелю |
| A2 | Team Lead | Очередь своей команды, загрузка ёмкости, состав роль—ФИО |
| A3 | Stakeholder / коллега | Просмотр плана, мониторинга и экспорт PDF по ссылке |
| A4 | Администратор развёртывания | Опубликовать приложение и общую БД (изолированно от v1) |

## 3. Use cases

### UC-01 — Просмотреть реестр проектов / продуктов

- **Акторы:** A1, A2, A3  
- **Триггер:** открытие приложения / вкладка «Реестр» / клик по логотипу «VI Planer»  
- **Предусловия:** загружено состояние (облако v2 / API `/api/state/v2` / localStorage `vi-planer-v2` / демо)  
- **Основной сценарий:**
  1. Система показывает метрики: активные функциональности, горизонт, команды под риском, старт планирования.
  2. Система показывает реестр проектов/продуктов (приоритет, RICE, ЧП/ROI при наличии, оценка, дата завершения); детали функциональностей — на «Потребность».
  3. Пользователь может раскрыть «Адженда» с легендой колонок.
- **Альтернатива:** нет данных → заполнение демо-seed.  
- **Постусловие:** пользователь видит актуальный реестр.

### UC-02 — Отфильтровать и отсортировать реестр

- **Акторы:** A1, A2  
- **Триггер:** фильтр / клик по заголовку колонки  
- **Сценарий:** поиск, тип, команда, статус; сортировка по Приоритет / RICE / Оценка / Дата завершения / финансы; сброс фильтров.  
- **Постусловие:** таблица отражает выбранный срез.

### UC-03 — Задать потребность по функциональности

- **Актор:** A1  
- **Триггер:** вкладка «Потребность»  
- **Сценарий:** выбор проекта → функциональности → назначение команд; у команды — роли из каталога (в т.ч. **бизнес-аналитик**, архитектор, аналитик, разработчик, тестировщик) с днями/майкой, статусом потребности и стартом; сохранение.  
- **Альтернативы:** нет команд в справочнике → сначала «Команды»; роли без состава команды ограничиваются настроенным списком роль—ФИО.  
- **Постусловие:** назначения и роли в состоянии; план и Gantt пересчитаны.

### UC-04 — Спланировать исполнителей

- **Акторы:** A1, A2  
- **Триггер:** вкладка «Планирование»  
- **Сценарий:** фильтр «Моя команда»; назначение исполнителя (ФИО из состава команды) на роль потребности; визуализация полосок назначений.  
- **Постусловие:** у ролей заполнен `assigneeId` где задано.

### UC-05 — Создать / редактировать / удалить функциональность (карточка)

- **Актор:** A1  
- **Триггер:** создание из Реестра / Потребности или клик по строке  
- **Сценарий:** поля (название, тип, продукт/проект, статус, заказчик, исполнитель, RICE, приоритет, заметки, опционально ЧП/ROI); команды с маечной оценкой XS–XXL и стартом; live RICE / дата завершения; сохранение / удаление.  
- **Постусловие:** портфель и расписание пересчитаны; приоритеты уникальны 1…n.

### UC-06 — Изменить сквозной приоритет

- **Актор:** A1  
- **Триггер:** ввод ранга / drag ⋮⋮  
- **Предусловие drag:** сортировка по «Приоритет»  
- **Сценарий:** новый ранг; при конфликте — confirm; переиндексация 1…n.  
- **Постусловие:** очереди и Gantt следуют новому порядку.

### UC-07 — Управлять командами и составом

- **Акторы:** A2, A1  
- **Триггер:** вкладка «Команды»  
- **Сценарий:** название; состав роль—ФИО (ёмкость = число людей); создание команды с цветом; роли для потребности берутся из состава.  
- **Альтернатива:** удаление команды — вне scope.

### UC-08 — Настроить маечную оценку и старт планирования

- **Акторы:** A1, A2  
- **Триггер:** вкладка «Настройки»  
- **Сценарий:** диапазоны дней XS–XXL; дата старта планирования; пакет портфеля из таблицы / откат.  
- **Постусловие:** оценки и горизонт пересчитаны.

### UC-09 — Просмотреть очередь команд

- **Акторы:** A2, A1  
- **Триггер:** «Очередь команд»  
- **Сценарий:** единый вид по всем командам: очередь по приоритету, план/сдвиг, даты, «может взять с…» / причина, утилизация 8 нед.; режимы утилизации (pill-кнопки); тоггл загрузки команд.  
- **Постусловие:** пользователь видит загрузку и слоты команд.

### UC-10 — Просмотреть сроки (Гант)

- **Акторы:** A1, A3  
- **Триггер:** «Гант»  
- **Сценарий:** полоски по командам, bottleneck, зависимости очереди (в последовательном режиме); горизонт 4–52 нед.; pill-кнопки **Последовательная** / **Максимальная** утилизация (повторный клик → «Как задано»); опционально полосы загрузки.  
- **Альтернатива:** статус «Готово» исключается из расписания.

### UC-11 — Просмотреть мониторинг (демо)

- **Акторы:** A1, A3  
- **Триггер:** вкладка «Мониторинг»  
- **Сценарий:** read-only: загрузка команд (слева) и **комплектация** (справа) — доля функциональностей с заполненными командой + заказчиком + исполнителем; общие режимы утилизации как на Ганте/Очереди.  
- **Постусловие:** пользователь видит демо-метрики без редактирования данных на вкладке.

### UC-12 — Просмотреть журнал изменений

- **Акторы:** A1, A2  
- **Триггер:** вкладка «Журнал»  
- **Сценарий:** список недавних изменений в приложении (локальный журнал состояния).  
- **Постусловие:** пользователь видит историю действий в SPA.

### UC-13 — Сохранить и синхронизировать данные (только v2)

- **Акторы:** A1, A2  
- **Триггер:** любое изменение  
- **Сценарий:** localStorage `vi-planer-v2` сразу; debounce → Supabase row `v2` и/или PUT `/api/state/v2`; индикатор синхронизации в шапке. Ключи v1 (`vi-planer-v3`, row `main`) **не** читаются и **не** пишутся.  
- **Альтернатива:** API/облако недоступны → локальный fallback.

### UC-14 — Скачать PDF текущей вкладки

- **Акторы:** A1, A3  
- **Триггер:** «Экспорт PDF» в шапке  
- **Сценарий:** цветной landscape A4 PDF метрик + активной вкладки; html2canvas и jspdf в бандле (без CDN).  
- **Альтернатива:** ошибка захвата → alert.

### UC-16 — Переключить редакцию v1 ↔ v2

- **Акторы:** A1, A3  
- **Триггер:** переключатель в шапке  
- **Сценарий:** переход на `/v1/` или корень v2; данные каждой редакции остаются в своём store.  
- **Постусловие:** другая редакция открыта без wipe чужого localStorage / cloud row.

### UC-17 — Открыть приложение по публичной ссылке

- **Акторы:** A3, A4  
- **Сценарий:** GitHub Pages (+ Supabase shared, row `v2`) / Railway·Render·VPS с Python FastAPI или Node Express / LAN.  
- **Альтернатива:** Pages без Supabase → данные per-browser (`VITE_LOCAL_STORAGE_ONLY`).

### UC-18 — Вернуться на главную (Реестр)

- **Акторы:** A1, A2, A3  
- **Триггер:** клик по бренду «VI Planer» в шапке  
- **Сценарий:** активная вкладка переключается на «Реестр».

## 6. Модель данных (v2)

### AppState
`version` (3), `startDate`, `teams[]`, `items[]`, `sizeRanges` (XS…XXL → min/max **дней**), `customers[]` / `executors[]`, `projects[]` / `products[]`, `changeLog[]`, опционально `portfolioPack`, миграционные флаги, `savedAt`

### Team
`id`, `name`, `capacityPw` (обычно = число людей), `color`, `members[]` (роль—ФИО), `roles[]`

### WorkItem (функциональность)
`id`, `title`, `type` (product|project), `backlog`, `status`, `owner` (Заказчик), `assignee` (Исполнитель), `assignments[]`, `reach`, `impact`, `confidence`, `notes?`, `manualRank`, опционально `cashFlow12m` / `roi12m`

### TeamAssignment
`teamId`, `size` (XS…XXL), `workStartDate` (понедельник), `roles[]` (потребность)

### AssignmentRole
`id`, `name` (каталог: бизнес-аналитик, архитектор, аналитик, разработчик, тестировщик), `size?`, `days?`, `demandStatus?`, `workStartDate?`, `assigneeId?`

### Расчётные (не persist)
`ScheduledSlice`, `ItemSchedule`, `TeamLoadWeek` — очереди, дата завершения, bottleneck, загрузка по неделям.  
Комплектация (Мониторинг): доля заполненных факторов команда / заказчик / исполнитель по активным функциональностям.

### Ключи хранения (только эта редакция)
| Слой | Ключ / id |
|---|---|
| localStorage state | `vi-planer-v2` |
| localStorage UI tab | `vi-planer-v2-ui-tab` |
| Supabase / Postgres | `app_state.id = 'v2'` |
| HTTP API | `/api/state/v2` |

## 7. Критерии приёмки (smoke)

1. Создать/назначить функциональность на 2 команды с ролями на Потребности.  
2. На Планировании назначить исполнителя из состава команды.  
3. Изменить приоритет drag в Реестре.  
4. Включить Последовательную или Максимальную утилизацию и увидеть сдвиг даты завершения на Ганте.  
5. Открыть Мониторинг — видны загрузка и комплектация (read-only).  
6. Экспорт PDF с активной вкладки (без CDN).  
7. Перезагрузить страницу — данные в `vi-planer-v2` / cloud `v2` сохранились.  
8. Переключить на v1 и обратно — данные v2 не стёрты; v1 store не тронут.  
9. Клик по «VI Planer» → Реестр.  
10. Скачать PDF требований; открыть PDF презентации.
